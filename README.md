## 담당 기능 & 문제 해결

### 1. 리뷰 신뢰도 관리 — 3단계 검증 흐름

- **문제:** 아무나 리뷰를 쓸 수 있고 욕설·광고 글이 그대로 노출되면, 리뷰가 핵심인 쇼핑 서비스의 신뢰도가 크게 떨어질 수 있었습니다.
- **해결:**
  1. **구매 확정 후에만 작성:** 주문 상태가 구매 확정일 때만 리뷰 작성 버튼이 활성화되도록 해, 실제 구매자만 리뷰를 남기게 했습니다.
  2. **금지어 자동 필터:** 서비스 레이어에서 금지어 리스트로 내용을 검사해, 부적절한 표현이 포함되면 DB에 저장하기 전에 등록을 막고 안내 모달을 띄웁니다.
  3. **신고 → 관리자 검토:** 필터를 통과한 글은 사용자 신고로 걸러냅니다. 사이트 관리자가 신고 목록에서 내용을 확인한 뒤 유지하거나 비활성화하고, 비활성화된 댓글은 삭제 대신 "운영 정책 위반으로 블라인드 처리" 문구로 치환해 대화 흐름은 유지했습니다.

### 2. 판매자 매출 흐름 — 주문 + 예약 통합 집계

- **문제:** 기존 매출 집계는 결제 완료된 주문만 기준으로 해서, 매장 방문 예약으로 발생한 판매가 빠져 있었습니다. 주문과 예약 데이터가 따로 있어 판매자가 실제 매출 흐름을 파악하기 어려웠습니다.
- **해결:**
  - Order와 Reservation 도메인을 함께 집계하는 구조로 쿼리를 재설계했습니다.
  - MyBatis Dynamic SQL로 기간 조건(주간 / 월간)에 따라 두 데이터를 합쳐 매출 추이, 이번 주 매출·주문 수, 매출 상위 상품 TOP 5를 계산합니다.
  - 집계 결과를 차트로 시각화해 판매자 대시보드에 연결했습니다.

### 3. 직원 권한 관리 — 3단계 RBAC

- **문제:** 매장의 모든 관리자 계정이 같은 권한을 가지고 있어, 직원 실수로 상품이나 매장 정보가 삭제될 위험이 있었습니다.
- **해결:**
  - 권한을 **마스터 / 중간관리자 / 사원** 3단계로 나눴습니다. 사원과 중간관리자는 수정만 가능하고, 삭제와 직원 관리(인사 권한)는 마스터만 할 수 있습니다.
  - 서비스 로직에 들어가기 전 Validator 계층에서 직급 권한을 검사하고, 권한이 없으면 예외를 발생시켜 경고 모달로 요청을 차단합니다.
  - 직원 계정 관리 화면에서 직원별 권한과 마지막 접속 시간을 확인할 수 있게 했습니다.

## 로컬 실행 방법

```bash
git clone https://github.com/KIMRAHUI/cors.git
cd cors

# application.properties(또는 .yml)에 DB 접속 정보와 아래 외부 API 키 설정
```

## 회고

- **데이터 정합성:** 주문과 예약처럼 성격이 다른 데이터를 하나의 지표로 합치면서, 화면보다 데이터 구조와 검증 로직을 먼저 설계해야 한다는 걸 배웠습니다.
- **사용자 관점:** 권한 분리나 접속 시간 표시처럼 작은 기능도, 실제 점주가 매장을 운영할 때 겪는 문제에서 출발해야 의미가 있다는 걸 느꼈습니다.
- **전체 흐름:** UI부터 백엔드 검증, DB 무결성까지 한 기능을 끝까지 연결해 보면서 프로그램 전체를 보는 시야를 넓혔습니다.
